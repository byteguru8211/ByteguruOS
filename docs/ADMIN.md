# Руководство администратора ByteguruOS

Для тех, кому нужен стол не «для себя», а для машины или парка машин: как
устроена конфигурация, где смотреть диагностику, что делать при отказе
загрузки и как пересобрать образ.

Справочники команд — в самой системе: `man bgwl`, `man bgctl`,
`man bginstaller`, `man bgd`, `man wcmgr`, `man byteguru-boot-repair`.
Здесь они не дублируются, а связаны с практикой.

---

## 1. Что и кем установлено

Пять пакетов, и границы между ними совпадают с границами кода:

| Пакет | Что несёт | Куда кладёт |
|---|---|---|
| `byteguru-compositor` | композитор `bgwl` | `/usr/bin/bgwl`, `man1/bgwl` |
| `byteguru-shell` | панель, палитра, лаунчер, настройки, локер, уведомления, `bgctl`, точка входа сеанса | `/usr/bin/bg*`, `python3/dist-packages/bgshell` |
| `byteguru-apps-daemon` | демон модели приложений `bgd` | `/usr/bin/bgd`, пользовательский юнит |
| `byteguru-installer` | установщик: планировщик, исполнение, окно | `/usr/bin/bginstaller{,-gui}`, `man8/bginstaller` |
| `byteguru-wincompat` | подсистема Windows-приложений (опциональная) | `/usr/bin/wcmgr`, манифесты WCV |
| `byteguru-data` | `.desktop`-файлы, wayland-сеанс, политики EFI, `man8/byteguru-boot-repair` | `/usr/share/...` |

Образ доукомплектовывается overlay-ом (`iso/overlay`, копируется в
`config/includes.chroot/` при каждой сборке): утилиты ремонта загрузки,
политики udev/udisks2, локаль, `INSTALL.txt`, службы
`byteguru-live-check` и `byteguru-autoinstall`.

Важное следствие: **overlay — единственный источник этих файлов**. Каталог
`config/includes.chroot/` — производный каталог: он не хранится в git,
править нужно `iso/overlay/`, иначе изменение потеряется при следующей
сборке.

## 2. Конфигурация стола

### Композитор

Один файл, приоритет `BGWL_CONFIG` → `$XDG_CONFIG_HOME/byteguru/bgwl.conf` →
`~/.config/byteguru/bgwl.conf`. Полный перечень ключей — `man bgwl`; здесь
то, что обычно правит администратор:

```ini
layout = tile                 # float | tile | even
gap-inner = 8
gap-outer = 12
border-width = 2
animations = true
anim-duration = 180
idle-timeout = 10             # минуты до блокировки

xkb-layout = ru,us
xkb-options = grp:alt_shift_toggle

workspace = 1:сборка:#f2a33d
workspace = 2:тест:#3ecf8e

rule = foot:workspace=2:layout=tile
bind = Ctrl+Super+T:terminal
command-Super+F1 = foot --title=справка
```

Что стоит знать про поведение:

- отсутствующий файл — не ошибка, заводские значения образуют полную
  конфигурацию;
- неизвестный ключ или модификатор — сообщение в журнал и **пропуск
  строки**, а не отказ запуска. Сломанная строка не должна лишать
  пользователя стола;
- `workspace =` переопределяет поток по индексу, остальные остаются
  заводскими;
- имена клавиш регистрозависимы (`T`, не `t`), а клавиши вне таблицы
  задаются числом evdev-кода.

### Оболочка

Настройки оболочки — в `~/.config/byteguru/shell.ini`, но править его руками
не рекомендуется: значения проверяются по схеме
(`bgshell/settings.py`), и окно настроек — тот же валидатор с интерфейсом.
Смысл в том, что интерфейс не может предложить значение, которое не пройдёт
проверку, — поэтому отдельного «рукописного» списка настроек в оболочке нет.

### Живое изменение без перезапуска

Всё, что применимо на лету, доступно через сокет:

```sh
bgctl set layout even
bgctl set gap-inner 12
bgctl set accent "#3ecf8e"
bgctl set ws-layout 2 tile     # раскладка конкретного потока
bgctl reflow
```

Это тот же путь, которым ходит панель, поэтому «сделали через `bgctl`» и
«сделали через интерфейс» — один и тот же код, а не два.

## 3. Диагностика

### Где смотреть

| Что | Где |
|---|---|
| композитор и оболочка | `~/.local/state/byteguru/session.log` |
| служба ремонта загрузки | `journalctl -u byteguru-boot-repair.service` |
| само-проверка live-образа | `journalctl -u byteguru-live-check.service` |
| состояние стола прямо сейчас | `bgctl status`, `bgctl --json status` |
| что композитор сообщает оболочке | `bgctl events` |
| загрузочная запись | `sudo byteguru-boot-status` |

`session.log` появился не для удобства: до него вывод композтора уходил в tty
автологина, который никто не листал и который перезапускается вместе с
сеансом. «Сеанс не поднялся» без журнала разбирается гаданием.

### Типовые отказы

**Стол не появился.** `session.log`, последние строки. Если там ошибка
бэкенда — проверьте `WLR_BACKENDS`; если «не создан сокет» — композитор
умер на старте, чаще всего из-за отсутствующего протокола блокировки или
права на DRM-устройство (сессия logind, группа `render`).

**Панель не видно, окна есть.** Панель — отдельный процесс, её отсутствие не
ломает сеанс. `pgrep -a bgpanel`; если процесс есть, но поверхности нет —
значит layer-shell не пред-загружен: панель запускают через обёртку
`/usr/bin/bgpanel`, а не `python3 -m bgshell.ui.panel` напрямую. Обёртка
нужна ровно потому, что `LD_PRELOAD=libgtk4-layer-shell` и `GDK_BACKEND`
должны быть заданы **до** инициализации дисплея, а из Python это сделать
уже нельзя.

**Окна «вполовину непрозрачные» или янтарные заголовки.** Это не настройки, а
исторические дефекты, уже исправленные; если видите снова — ищите регрессию в
`util.c` (буфер заголовка обязан быть XRGB8888, а не ARGB: cairo работает с
premultiplied BGRA).

**Ничего не помогает.** `bgctl quit` и вход заново: состояние сеанса живёт в
композиторе, и перезапуск — штатный способ «начать с чистой конфигурации»,
а не варварство.

## 4. Соседство с Windows

### Часы

По умолчанию обе системы в UTC — это единственная политика, при которой они
не дерутся за одни и те же часы. Если выбрано `localtime` (например, потому
что на машине стоит софт, требующий именно такого времени), нужно
согласовать Windows: `bginstaller clock --windows --policy localtime`
показывает нужную команду реестра. Политика записывается в `/etc/adjtime`
установленной системы при установке, а не «как-нибудь потом».

### NTFS

Том Windows монтируется **только для чтения** — это политика udisks2 из
overlay, а не настройка пользователя. Разовая запись:
`mount -o remount,rw`. Постоянная — переключатель «Запись на NTFS» в окне
настроек (требует прав администратора).

### Порядок загрузки

Крупное обновление Windows переписывает UEFI BootOrder, и машина возвращается
в Windows. В установленной системе это лечится автоматически:
`byteguru-boot-repair.service` при запуске сравнивает порядок и возвращает
ByteguruOS на первое место. Вручную:

```sh
sudo byteguru-boot-status            # что прошивка знает сейчас
sudo byteguru-boot-repair            # что собирается сделать
sudo byteguru-boot-repair --apply    # сделать
```

Если прошивка не принимает NVRAM-записи (бывает после сброса параметров),
работает путь `\EFI\boot\bootx64.efi` — `grub-install --removable`.

### Однократная загрузка в Windows

`bginstaller boot-next --target windows` — разовый `BootNext`, без изменения
порядка. Из стола то же самое в меню питания.

## 5. Windows-приложения

Подсистема **выключена по умолчанию**. Пока `wincompat.enabled=false`,
оболочка не показывает ни эти приложения, ни обходные уровни L3/L4 — ни
списком, ни поиском.

Включение: окно настроек → «Windows-приложения» (требует прав). Дальше —
`wcmgr` (`man wcmgr`): `check`, `install`, `launch`, `record`, `rollback`,
`doctor`.

Что стоит понимать перед включением:

- уровень покрытия публикуется только по успешным прогонам. Заявленное в
  манифесте «работает» остаётся «не проверено», пока прогон не записан в
  реестр;
- изоляция — AppArmor + seccomp с deny-списками, которые манифест снять не
  может; `network.mode=open` и `no_new_privs=false` не проходят схему;
- системные корни нельзя открыть как литеру, и проверяется и нормальный путь,
  и разрешение символьной ссылки.

## 6. Сборка и проверка образа

Порядок шагов важен, потому что `build-iso.sh` **не** пересобирает пакеты:

```sh
bash build/scripts/build-packages.sh      # .deb → config/packages.chroot/
sudo bash build/scripts/build-iso.sh      # образ → build/out/
sudo bash build/scripts/boot-smoke-test.sh        # live-сессия в QEMU
sudo bash build/scripts/install-smoke-test.sh     # установка + загрузка с диска
```

Что нужно знать, чтобы не потерять час:

- **Единственный согласованный способ пересобрать после сбоя — `--clean`.**
  `lb clean` не снимает отметки стадий в `.build/`, а следующий прогон по ним
  «этап уже сделан» для стадии, чей результат удалён. Классический
  симптом — `cp: cannot stat chroot/boot/vmlinuz-*`: ядро ставится стадией
  chroot, отметка о которой пережила снос chroot.
- **KVM обычно нет** — ни на dev-машине, ни на GitHub-runner. QEMU работает
  на TCG, и гость живёт в разы медленнее часов: отсюда `INSTALL_TIMEOUT` в
  минутах, а не секундах. Тест с таймаутом «пять минут» красный без причины.
- **`grub-pc` в образ положить нельзя**: он `Conflicts` с
  `grub-efi-amd64`, и сборка падает на неразрешимой паре. Значит live-образ
  умеет ставить только UEFI-загрузчик, а `--boot legacy` отказывает на этапе
  плана — до первого прикосновения к диску.
- **Имена пакетов проверяются по индексу trixie**:
  `python3 build/scripts/check-package-names.py`. Это не формальность:
  `dbus-tools` в trixie отсутствует, и сборка падала на этом за три стадии
  до результата.

### Что именно подтверждает каждый прогон

| Прогон | Утверждение |
|---|---|
| `verify-live-rootfs.sh` | rootfs пригоден для входа (статически, пока chroot жив) |
| `boot-smoke-test.sh` | образ грузится до `graphical.target` и даёт рабочий сеанс (`BYTEGURU-SESSION-OK`) |
| `install-smoke-test.sh` | установка на диск завершается, и с этого диска машина загружается сама |
| `desktop-shot.sh` | интерфейс выглядит как задуман (кадры читаются как картинки) |

CI (`/.github/workflows/iso.yml`) собирает образ в контейнере
`debian:trixie`, скачивает артефакт и прогоняет его в QEMU отдельным job'ом;
`lint-shell` проверяет `bash -n`, shellcheck и `.desktop`-файлы.

## 7. Обновление системы из исходников

```sh
git pull
ninja -C build-c                    # композитор
bash build/scripts/build-packages.sh
sudo bash build/scripts/build-iso.sh --clean
```

После правки в `src/shell` или `src/installer` пересборка пакетов
обязательна: образ берёт `.deb` из `config/packages.chroot/` и не смотрит на
исходники.

## 8. Чего в системе сознательно нет

- **XWayland** — X11-приложения не запустятся вообще. Это не «забытая
  галочка», а отдельный слой: в образе нет и X-сервера.
- **greeter** — вход делает autologin через getty. Свой экран приветствия с
  паролем и выбором сеанса в плане, но не реализован.
- **immutable root и A/B-обновления** — решение К4 зафиксировано, в образе
  первой сборки его нет.
- **Secure Boot, TPM, IMA** — задел только в defconfig и RFC.
- **Bluetooth** — пока у оболочки нет соответствующей панели, это мёртвая
  иконка, поэтому стека в образе нет намеренно.
