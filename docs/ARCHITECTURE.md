# Архитектура ByteguruOS

Документ описывает, как система устроена **сейчас**, в репозитории: что связано
границами, кто кому принадлежит и где обещания из плана разработки уже
подтверждены кодом, а где ещё нет.

## 1. Слои и границы

```
┌─────────────────────────────────────────────────────────────┐
│ Приложения: Flatpak (Linux) · WCV (Windows, опционально) · веб│
├─────────────────────────────────────────────────────────────┤
│ Оболочка (src/shell)                                        │
│   bgpanel · bgline · bglauncher · bgsettings · bgfirstboot  │
│   bgnote · bglock · bgctl                                   │
│   модель состояния: bgshell.ctl (сокет композитора)         │
├─────────────────────────────────────────────────────────────┤
│ Демон сеанса (src/bytegurud)                                │
│   единая модель приложений + план запуска (unix socket)     │
├──────────────────────────┬──────────────────────────────────┤
│ WinCompat (src/wincompat)│ Установщик (src/installer)        │
│ манифесты · окружения ·   │ разметка · проверки · исполнение │
│ изоляция · уровни L0–L4   │ · GTK-окно · ремонт EFI · часы   │
├──────────────────────────┴──────────────────────────────────┤
│ Композитор bgwl (src/compositor, C/wlroots)                 │
│   потоки · тайлинг · сокет управления · сеанс/блокировка    │
├─────────────────────────────────────────────────────────────┤
│ Системные сервисы: systemd · NetworkManager · PipeWire ·    │
│ CUPS · Flatpak · udisks2                                    │
├─────────────────────────────────────────────────────────────┤
│ Ядро Linux 6.x LTS + defconfig (build/configs)              │
├─────────────────────────────────────────────────────────────┤
│ Загрузка: UEFI · systemd-boot(UKI) / GRUB · ESP             │
└─────────────────────────────────────────────────────────────┘
```

Три правила, которые держат границы:

1. **WinCompat не трогает железо напрямую.** Только через протоколы сеанса:
   Wayland, PipeWire, CUPS, udev-прокси. Поэтому подсистему можно выключить
   целиком, и система останется работоспособной.
2. **Оболочка не знает форматов пакетов.** Она спрашивает у `bgd`, что
   установить/запустить, и получает план. Flatpak, WCV и системный образ для неё
   выглядят одинаково.
3. **Изменение разметки и EFI — прерогатива установщика.** Оболочка вызывает его
   API (`bginstaller boot-repair`, `boot-next`), а не пишет в `efibootmgr` сама.

## 2. Подсистема WinCompat

Подсистема **опциональна и по умолчанию выключена** (`wincompat.enabled=false`):
ByteguruOS — своя система, а не обёртка над Wine. Пока она выключена,
оболочка не показывает ни wincompat-приложения, ни обходные уровни L3/L4 —
ни списком, ни поиском (фильтр стоит в `bgshell.ui.bggui.Session`, а не в
демоне: демон обязан знать все источники, решение «показывать» — продуктовое).

Модули и их ответственность:

| Модуль | Обязанность | Ключевое решение |
|---|---|---|
| `manifest.py` | схема WCV, валидация, каноническая сериализация | неизвестный ключ = ошибка; `network.mode=open` запрещён; `no_new_privs=false` запрещён |
| `prefix.py` | хранилище окружений, версии, откат | один префикс на приложение; версии неизменяемы, `CURRENT` — указатель |
| `drives.py` | литеры C:/Z: и фильтр видимости путей | проверка и нормализованного пути, и разрешения символьной ссылки |
| `sandbox.py` | AppArmor-профиль, seccomp-профиль, свойства юнита | жёсткие deny-списки, которые манифест не может снять |
| `fallback.py` | выбор пути L0–L4 по доказанному уровню | нет «придумать патч на лету», только закрытый набор действий |
| `spawn.py` | векторы команд wine/qemu/systemd-run | никаких выдуманных флагов Wine; чистые функции без исполнения |
| `registry.py` | реестр совместимости | опубликованный уровень = максимум успешных прогонов; L3/L4 не доказывают L1 |
| `cli.py` | `check/install/launch/list/record/rollback/export/doctor` | по умолчанию печатает план, `--run` только в Linux |

Поток запуска:

```
bgd.launch_plan(id)
  → load_manifest(prefix/manifest.wcv)
  → registry.proven_level(id)          # доказанный уровень, не заявленный
  → capabilities()                     # KVM, Windows-раздел, /dev/dri
  → fallback.decide(...)               # launch-wine | launch-vm | reboot-to-windows | unsupported
  → sandbox.build_plan(...)            # AppArmor + seccomp + свойства юнита
  → spawn.build_wine_command + scope   # systemd-run → aa-exec → wine
```

Оболочка показывает именно этот план, и пользователь видит команду до запуска.

## 3. Установщик и соседство с Windows

`Disk`/`Partition` — неизменяемые модели, получаемые из `lsblk`/`sfdisk` (разбор
отделён от исполнения, поэтому тестируется без root и без Linux).

- `safety.evaluate()` — реестр замечаний с уровнями `block/warn/info`. Гибернация,
  BitLocker, грязный NTFS — блокируют; неизвестный «быстрый запуск», малый ESP,
  батарея — предупреждают.
- `planner._place()` — first-fit-decreasing по **непрерывным** областям. Сумма
  свободных промежутков не считается пригодным местом: 1 ГиБ щель не войдёт в
  50-ГиБ раздел.
- `planner.plan()` — при нехватке места подбирает сжатие NTFS шагом, никогда не
  оставляя Windows меньше 30 ГиБ, и останавливается на блокирующих проверках.
- `apply.apply_plan()` — dry-run по умолчанию; необратимые действия пропускаются
  без токена и останавливают цепочку при первой ошибке.
- `operations.commands_for()` — превращает действие плана в настоящие команды:
  `parted`/`mkfs.*`/`rsync`/`grub-install`/`efibootmgr`. Раньше здесь стояли
  бинарники `bg-mount-target` и `bg-image-install`, которых не существует, —
  поэтому «установка» всегда разваливалась на первом привилегированном шаге.
  Данные (пароль, содержимое `/etc/fstab`) уходят через stdin или запись файла,
  а не через подстановку в argv.
- `ui/installer.py` — окно установщика: язык → диск → пользователь → план со
  списком команд → прогресс с логом → готово. Прогон идёт в рабочем потоке,
  потому что `rsync` rootfs занимает минуты, и «окно думает» без единой строки
  — это то, из-за чего пользователь выдёргивает флешку.
- `bootrepair`/`clock` — ремонт BootOrder после Windows и политика часов
  (по умолчанию: обе системы в UTC, с явной командой `reg add` для Windows).

## 4. Демон и оболочка

`bgd` объединяет источники (Flatpak, WCV, .desktop) в `Application` с полем
`evidence`, поэтому интерфейс не может показать непроверенное как проверенное.
Дедупликация предпочитает нативное Linux-приложение, вариант WinCompat сохраняется
в `extra.variants`.

`bgshell` разделён нарочно: `ctl.py`, `settings.py`, `themes.py`, `fuzzy.py`,
`systeminfo.py` — чистая логика с тестами; `ui/` — GTK-слой, который читает
модель. Благодаря этому поведение панели и палитры проверяется без дисплея, а
GTK-код остаётся тонким.

Единственный источник истины о окнах и потоках — сокет управления композитора
(`$XDG_RUNTIME_DIR/byteguru/compositor.sock`), а не собственный список оболочки:
панель, `bgctl` и Guru Line читают одно и то же состояние, поэтому не могут
разойтись. `bgshell.ctl.EventSource` держит отдельное подписанное соединение и
перерисовывает виджеты на `EV <kind>`.

Guru Line (`bgline`, Super+Esc) — не «ещё один лаунчер»: одна строка принимает
приложения, потоки, раскладки, действия сеанса и переключатели. Порядок
кандидатов считает `bgshell.fuzzy` (начало строки > начало слова >
подпоследовательность), поэтому «бр» даёт браузер, а не «совпадений нет».

## 5. Композитор

`bgwl` — C поверх wlroots 0.18.2 (ровно та версия, что в Debian 13; meson ищет
0.18 → 0.19 → 0.20). Код собирается и работает: проверка — headless-сеанс,
`grim`-снимки и pytest против сокета управления.

Реализовано:

- **Потоки** (`workspace.c`) — по одному дереву сцены на поток. Переключение
  стоит O(1) (сменить активное дерево), а не «переложить все окна», и
  сопровождается анимацией сдвига (`anim.c`); акцент потока служит цветом
  рамки фокуса.
- **Тайлинг** (`tiling.c`) — `float` / `tile` (мастер + полоса стека) / `even`
  (равная сетка), зазоры, `master_pct`, поворот стека; перестройка — в одном
  месте, `bgwl_workspace_set_layout`, поэтому смена раскладки не оставляет
  окон в прежней геометрии.
- **Сеанс** (`session.c`) — двухступенчатый простой (сначала блокировка,
  потом DPMS), ext-session-lock с обязательным `locked` после коммита всех
  поверхностей, авто-разблокировка при смерти клиента блокировки, закрытие
  крышки → команда блокировки.
- **Сокет управления** (`ctl.c`) — текстовые команды в JSON-ответами и
  события `EV <kind>`; единственный способ, которым оболочка узнаёт состояние
  окон.
- Протоколы (`protocols.c`) — xdg-shell, layer-shell, session-lock,
  idle-notify, output-management, screencopy, fractional-scale + viewporter,
  cursor-shape, data-control, foreign-toplevel, input/text-input,
  security-context (Flatpak). Несущественные не убивают сеанс: отсутствие
  dmabuf на программном рендере — норма, а вот без lock/idle сеанс не собирается.
- Ввод (`input.c`) — таблица встроенных комбинаций, Alt+перетаскивание,
  изменение размера за край, клик по кнопкам заголовка, маршрутизация клавиш
  в заблокированном сеансе.
- Заголовки окон рисует cairo (`util.c`), включая кнопки и обрезку длинных
  имён; буфер заголовка — XRGB8888, иначе прозрачная подложка даёт янтарную
  полосу вместо читаемого текста.

Не реализовано: XWayland (в образе нет X-сервера), `output-power-management`
(XML-описание не поставляется в wlroots 0.18; DPMS делается внутренним
вызовом), анимации появления/закрытия окна — в 0.18 прозрачность задаётся на
буфер, а не на узел, и «плавное затухание» превращалось в окно, застрявшее на
половине непрозрачности.

## 6. Сборка образа

`build/scripts/build-iso.sh` — единственная точка входа; внутри `lb config` +
`lb build` по конфигу из `build/live/`. CI (`/.github/workflows/iso.yml`) выполняет
сборку **внутри контейнера `debian:trixie`**: конфиг написан по документации
trixie, а live-build на ubuntu-24.04 (3.0~a57) и debootstrap 1.0.134 про trixie не
знают. Артефакт — гибридный ISO + SHA256.

Порядок такой, потому что `build-iso.sh` не пересобирает пакеты: `.deb`
берутся из `config/packages.chroot/`, и после правки в `src/` нужен
`build-packages.sh`. Единственный согласованный способ пересобрать образ
после сбоя — `--clean`: `lb clean` не трогает отметки стадий в `.build/`, а
следующий прогон по ним «уже сделано» для стадии, чей результат удалён
(отсюда историческое `cp: cannot stat chroot/boot/vmlinuz-*`).

Overlay (`iso/overlay`) привозит в образ: `byteguru-boot-repair`,
`byteguru-boot-status`, `byteguru-vboxsf-mount`, `byteguru-live-check`,
udev/udisks2-политику NTFS-только-для-чтения, локаль/раскладку и
`INSTALL.txt`.

Цепочка проверки — три разных вопроса, и смешивать их нельзя:

| Что спрашиваем | Чем |
|---|---|
| rootfs пригоден для входа | `build/scripts/verify-live-rootfs.sh` (статически, пока chroot жив) |
| образ загружается и даёт сеанс | `build/scripts/boot-smoke-test.sh` + `byteguru-live-check` внутри образа: на консоли появляется `BYTEGURU-SESSION-OK` |
| интерфейс выглядит как задумано | `build/scripts/desktop-shot.sh` — кадры headless-сеанса, которые читаются как картинки |

Прогон в QEMU идёт без KVM (ни на dev-машине, ни на runner его нет), то есть
на TCG: гость живёт в разы медленнее часов, отсюда таймаут в минутах, а не в
секундах. Раньше это выглядело как «тест красный без причины».

## 7. Что ещё не связано в систему

- **Исполнение планов WinCompat.** `spawn` строит векторы, но ни один из них не
  запускался против настоящего Wine: проверка DXVK-путей, печати и звука — впереди.
  То, что подсистема опциональна, уже обеспечено кодом: при
  `wincompat.enabled=false` оболочка убирает её приложения и из списка, и из
  поиска (`bgshell.ui.bggui.Session`), а не только прячет значок.
- **XWayland.** Без него не запускаются X-only приложения; в образе нет и
  X-сервера, поэтому это не «забытая галочка», а отдельный слой.
- **Экран приветствия.** Вход в систему делает autologin через getty; свой
  greeter с паролем и выбором сеанса — в списке задач.
- **Пакетирование.** Компоненты собраны в `.deb` и лежат в
  `config/packages.chroot/`, но live-образ устанавливает их без подписанного
  репозитория: обновляемость через apt появится вместе с immutable root.
- **Immutable root и A/B.** Решение К4 зафиксировано, но в образе первой сборки
  его нет: сначала — простой устанавливаемый live-образ.
- **Обновления, UKI/Secure Boot, TPM, IMA.** Задел только в defconfig и RFC.
- **Карточки уведомлений.** D-Bus-сервис, история и показ работают; поверхность
  layer-shell не может быть меньше 200x200 (минимум GtkWindow), поэтому под
  одной карточкой остаётся прозрачная полоса, перехватывающая клики.

## 8. Как читать состояние проекта

`README.md` — таблица «что проверено»; `docs/rfcs/` — решения с обоснованием;
`docs/ByteguruOS-plan.docx` — план и дорожная карта; `git log` — что уже реально
сделано. Расхождение между этими документами — дефект, его надо править.
