# RFC 0002: двухзагрузочный режим — решения К11 и К12

Статус: принят, реализован в `src/installer/` частично (планирование, проверки,
ремонт EFI, политика часов); применение к реальному диску не проверялось.

## Мотивация

На машине, где Windows убрать нельзя, ОС без поддерживаемого соседства не имеет
шанса: пользователь либо остаётся на Windows, либо устанавливает нашу систему
вторым диском и теряет half-года обновлений. Dual boot — не «опция для энтузиастов»,
а вход в реальный парк. Требование зафиксировано владельцем проекта отдельно.

## Ключевые решения

### К11 — загрузчик

Основной путь: **systemd-boot + UKI** (unified kernel image), запись
`\EFI\byteguru\systemd-bootx64.efi`. Chainload Windows — стандартная EFI-запись
Boot Manager, трогать её содержимое мы не имеем права.

Альтернатива `GRUB` поддерживается для Legacy/CSM и для машин, где systemd-boot не
проходит из-за особенностей UEFI. Live-образ при этом собирается с GRUB/isolinux
(гибридный ISO), а **установленная** система — systemd-boot. Расхождение
задокументировано в `iso/overlay/etc/efi-boot-policy.env`, а не оставлено как
неожиданность.

Обоснование: UKI предсказуем (ядро + initrd + cmdline в одном подписанном файле),
что важно для целостности и для отзыва ключей; GRUB дороже в безопасности и чаще
ломается после обновлений Windows.

### К12 — том Windows и обмен данными

- NTFS монтируется **только для чтения** по умолчанию (udev-правило +
  `udisks2/mount_options.conf`), включая случай «пользователь очень просит».
- Если на томе есть `hibernafil.sys`/признаки гибернации — монтирование на запись
  блокируется безусловно: это гарантированное повреждение чужой системы.
- Общая обменная область — отдельный **exFAT**-том, создаваемый установщиком по
  желанию. Выбор exFAT: нативная запись в ядре Linux 6.x и в Windows без патчей.
- Запись на NTFS включается настройкой `storage.ntfs-write` (по умолчанию `false`)
  и требует прав администратора.

### Разметка

Один диск, типичный порядок разделов после установки рядом:

```
p1 EFI System (FAT32, переиспользуется, не переформатируется)
p2 Microsoft reserved (MSR)        — не трогаем
p3 Windows (NTFS)                  — сжатие только при выполненных проверках
p4 Recovery                        — не трогаем и не перемещаем
p5.. BG root (immutable-задел)     — 25–40 ГиБ
p6.. BG /var (btrfs)               — 60–120 ГиБ, самый быстрорастущий
p7.. BG /home (btrfs + LUKS)       — остаток
p8.. shared (exFAT)                — опционально
```

Правило: **ни один раздел ByteguruOS не является единственным носителем данных
пользователя.** `/home` и `/var` отдельны от system, поэтому переустановка и откат
не требуют бэкапа «всего».

### Почему сжатие считается по непрерывным областям

Раздел обязан быть непрерывным. Сумма свободных промежутков — не объём, доступный
для размещения: промежуток в 1 ГиБ не станет частью 50-ГиБ раздела. Планировщик
размещает разделы first-fit-decreasing по реальным промежуткам, а дефицит места
покрывает сжатием NTFS шагом, оставляя Windows не менее 30 ГиБ.

### Блокирующие проверки перед любым изменением разметки

| Условие | Реакция |
|---|---|
| гибернация Windows (`hiberfil.sys`) | блок: полное завершение работы |
| BitLocker без приостановки | блок: `manage-bde -protectors -disable` |
| «грязный» NTFS | блок: chkdsk в Windows |
| UEFI, но таблица MBR | блок: GPT обязателен |
| неизвестно про «быстрый запуск» | предупреждение + рекомендация |
| ESP < 512 МиБ | предупреждение: может потребоваться пересоздание (тронет загрузчик Windows) |
| работа от батареи, съёмный диск | предупреждение |

### Политика часов

По умолчанию — **обе системы в UTC** (`boot.clock-policy = windows-utc`): единственный
режим, в котором часы не расходятся после переключения. Установщик печатает команду
`reg add ... /v RealTimeIsUniversal /t REG_DWORD /d 1 /f`, которую должен выполнить
администратор Windows: из Linux мы её не применяем и не делаем вид, что можем.

Альтернатива `localtime` (мы подстраиваемся под Windows) доступна, но маркируется
как историческая.

### Ремонт после обновлений Windows

Обновление или переустановка Windows часто перезаписывает `BootOrder`, и ByteguruOS
исчезает из меню. Это штатное событие, поэтому в системе лежит
`byteguru-boot-repair`:

- если наша EFI-запись есть — только поднимает её в начале `BootOrder` и снимает
  флаг неактивности;
- если записи нет — создаёт её заново (`efibootmgr -c` с путём к systemd-boot);
- **никогда не удаляет чужие записи**, включая Windows Boot Manager;
- работает в режиме `--dry-run` по умолчанию.

Однократная перезагрузка в Windows — `BootNext`, без изменения постоянного порядка
(`bginstaller boot-next --target windows`).

### TPM и Secure Boot

Обе системы используют один TPM2: пространства NV-индексов разносятся, процедура
сброса описана. Привязка данных к TPM невозможна без PIN-фолбэка, иначе вторая ОС
лишает доступа к дому. Secure Boot на двухзагрузочной машине допускается, только
если наш PKC импортирован в EFI; иначе честная рекомендация — выключить.

## Что остаётся непроверенным

- Поведение UEFI конкретных вендоров при создании второй EFI-записи (именно там ломается
  больше всего) — нужна аппаратная лаборатория.
- Применение плана к реальному NTFS: `ntfsresize` в связке с состояниями гибернации.
- Совместимость нашего PKC с Secure Boot на разных прошивках.
