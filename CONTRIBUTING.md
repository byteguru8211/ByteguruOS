# Как участвовать

## Окружение разработки

Нужен Python 3.11+; Linux не обязателен для тестов ядра подсистем, но обязателен
для сборки образа и проверки интерфейса.

```sh
python -m venv .venv && . .venv/bin/activate
pip install pytest
pytest -q
```

Запуск подсистем локально (без установки в систему):

```sh
PYTHONPATH=src/wincompat:src/installer python -m wcmgr.cli check data/wincompat
PYTHONPATH=src/installer python -m bginstaller.cli plan --disk-file tests/fixtures/lsblk-dualboot.json
PYTHONPATH=src/bytegurud:src/wincompat python -m bgd.cli --wcv-dir data/wincompat --registry /tmp/r.db apps
```

## Правила кода

- **Комментарий объясняет почему, а не что.** Строки вида `# увеличиваем счётчик`
  не нужны: имена обязаны справляться сами.
- **Никаких выдуманных интерфейсов.** Флаг, пакет, API или поле схемы, которых не
  существует, — это не «заготовка», а будущая авария. Если сомневаетесь —
  оставляйте маркер `ВЕРИФИЦИРОВАТЬ: что именно проверить и против чего`.
- **Чистые функции для принятия решений, исполнение — отдельно.** Планировщик
  разметки, генератор политик и сборщик команд ничего не делают сами; исполнение
  требует явного `--apply`/`--run` и происходит в одном месте.
- **Неизвестные данные — риск, а не разрешение.** Неизвестный ключ манифеста,
  незнакомая настройка, неизвестное состояние «быстрого запуска» Windows
  останавливают операцию или уводят её в предупреждение.
- **Линейки LF, UTF-8.** См. `.editorconfig` и `.gitattributes`; CRLF в shell- и C-файлах ломает сборку на Linux-раннере.

## Тесты

- Каждый новый модуль — с тестами в `tests/`, включая негативные: неверный ввод
  обязан быть отвергнут с объяснимым сообщением.
- Фикстуры вывода системных утилит кладутся в `tests/fixtures/` как есть,
  с комментариями, на какой версии утилиты они получены.
- Тест, который нельзя запустить без root/железа, помечается `@pytest.mark.skipif`
  с причиной — но не удаляется.

## Процесс изменений

1. Ветка от `main`, имя по смыслу: `wincompat/network-proxy`, `installer/esp-reuse`.
2. PR обязан содержать: что меняется, почему, **что проверено и чем**, а что
   осталось непроверенным. Формулировка «должно работать» не принимается.
3. CI: `tests.yml` (pytest) и `iso.yml` (сборка образа). Красный `tests.yml`
   блокирует слияние; `iso.yml` пока informativен — первая успешная сборка
   переведёт его в блокирующие.
4. Изменения в архитектуре (уровень решений К1–К12) — только через RFC в
   `docs/rfcs/`, с явным указанием, что ломается у существующих пользователей.
